用交互式 rebase 整理你的提交历史

适用场景：本地分支上有若干零碎提交（fix typo、wip、debug），推送之前希望整理成干净的几条记录。

第一步，确定范围。git rebase -i HEAD~3 表示整理最近 3 个提交；git rebase -i origin/main 表示整理当前分支相对 main 分叉之后的所有提交。范围开区间是"不包含"，所以 HEAD~3 实际是最近三个提交，不含 HEAD~3 本身。

第二步，编辑待办列表。编辑器打开后每一行是 "<动作> <哈希> <提交信息>"，从上到下就是提交被重新应用的顺序。这点很关键：调整行的先后顺序，就等于重排提交顺序；把两行对调，重放时后一个改动会先落地，冲突的可能也随之改变。

可用动作：
pick 保留该提交（默认）
reword 保留内容，修改提交信息
edit 停在该提交上，允许修改内容后再继续
squash 合并进上一个提交，保留本条提交信息供编辑
fixup 合并进上一个提交，丢弃本条提交信息
drop 删除该提交

squash 与 fixup 的区别只在提交信息：squash 会把两条信息拼在一起让你编辑，fixup 直接丢弃被合并那条的信息。整理历史时通常用 fixup 清理 wip 提交，用 squash 合并需要保留说明的提交。

第三步，处理冲突。rebase 过程中一旦冲突，git 会停下来并在输出中提示当前停在哪一步。解决冲突文件后执行 git add <文件>，再执行 git rebase --continue。如果发现搞错了，git rebase --abort 会把分支恢复到 rebase 开始前的状态，这是唯一无损的退出方式；不要用 git reset --hard 代替，它可能丢掉已经改好的部分。

第四步，修改很久以前的提交内容。把目标行改成 edit，保存退出后 git 会停在该提交上，此时修改文件，git add 之后执行 git commit --amend --no-edit，再 git rebase --continue 继续重放后续提交。

黄金规则：不要 rebase 已经推送到共享分支的提交。rebase 会重写提交哈希，其他人基于旧哈希的工作会产生重复提交和难以理解的冲突。只整理尚未共享的本地历史，或者团队明确约定可以强推的分支。

补充一点：rebase 之后如果原本推过分支，需要 git push --force-with-lease 而不是 --force，前者会在远端被别人更新过时拒绝推送，避免覆盖他人的提交。
