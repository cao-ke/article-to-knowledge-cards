# 知识卡片：用交互式 rebase 整理你的提交历史

原文约 1100 字，提取 8 张卡片。

> 原文属高信息密度操作教程，取到上限 8 张。六种动作已合并为一张清单卡，其余各点分别对应范围语义、行序、冲突退出、旧提交修改、共享历史与强推，互不可合并。

---

## 卡片 1｜rebase -i 的范围是左开区间

**核心知识：** `HEAD~3` 指最近三个提交，不包含 `HEAD~3` 指向的那个提交本身。

**简明解释：** `git rebase -i HEAD~3` 整理最近 3 个提交；`git rebase -i origin/main` 整理当前分支自 main 分叉之后的全部提交。因为范围是开区间，起点提交不会被纳入。

**例子：** `git rebase -i HEAD~3`；`git rebase -i origin/main`

---

## 卡片 2｜待办列表的顺序就是重放顺序

**核心知识：** 待办列表自上而下即提交重新应用的顺序，调整行序等于重排提交。

**简明解释：** 每行格式为"动作 + 哈希 + 提交信息"。把两行对调，后一个改动会先落地，冲突出现的可能也随之改变。因此行序是比动作选择更需要先想清楚的部分。

**自测：** 在待办列表里对调两个 pick 行，直接结果是什么？

> 参考答案要点：两个提交的重新应用顺序被交换，冲突点可能随之改变。

## 卡片 3｜六种动作构成完整编辑能力

**核心知识：** pick、reword、edit、squash、fixup、drop 六种动作覆盖保留、改信息、改内容、合并、删除。

**简明解释：** 各动作的差异：pick 原样保留；reword 保留内容只改提交信息；edit 停在该提交上允许修改内容后继续；squash 并入上一提交并保留本条信息供编辑；fixup 并入上一提交且丢弃本条信息；drop 删除该提交。整理历史时的动作选择，本质上是在"保留多少信息"与"合并多少提交"之间取值。

**例子：** 原文动作表：`pick` / `reword` / `edit` / `squash` / `fixup` / `drop`

---

## 卡片 4｜squash 与 fixup 只差提交信息

**核心知识：** 两者都并入上一提交，squash 保留本条信息供编辑，fixup 直接丢弃。

**简明解释：** 唯一的差别在提交信息的处理：squash 把两条信息拼接后让你编辑，fixup 丢弃被合并那条。实践取舍是清理 wip 类提交用 fixup，需要保留说明的合并用 squash。

**例子：** 原文的取舍：清理 wip 提交用 `fixup`，合并需保留说明的提交用 `squash`。

---

## 卡片 5｜冲突时用 --continue，退出用 --abort

**核心知识：** 冲突解决后 `git add` 加 `--continue`；要放弃整轮整理只能用 `--abort`。

**简明解释：** rebase 遇冲突会停下并提示停在哪一步。解决冲突文件后先 `git add <文件>`，再 `git rebase --continue`。`git rebase --abort` 把分支恢复到开始前的状态，是唯一无损的退出方式；不要用 `git reset --hard` 代替，它可能丢掉已经改好的部分。

**例子：** `git add <文件>` → `git rebase --continue`；放弃则 `git rebase --abort`

## 卡片 6｜改旧提交用 edit 加 amend

**核心知识：** 把目标行改为 `edit`，停下后用 `commit --amend --no-edit` 改内容再继续。

**简明解释：** `edit` 会让 rebase 停在该提交上，此时修改文件、`git add` 后执行 `git commit --amend --no-edit`，再 `git rebase --continue` 重放后续提交。这是修改很久以前某条提交内容的标准路径。

**例子：** `git commit --amend --no-edit` → `git rebase --continue`

---

## 卡片 7｜不要 rebase 已推送到共享分支的提交

**核心知识：** rebase 会重写提交哈希，共享历史被重写会让协作者产生重复提交与冲突。

**简明解释：** 只整理尚未共享的本地历史，或团队明确约定可以强推的分支。哈希被重写后，他人基于旧哈希的工作无法与新历史对齐，从而产生重复提交和难以理解的冲突。

**自测：** 为什么在共享分支上 rebase 会伤害协作者？

> 参考答案要点：提交哈希被重写，他人基于旧哈希的提交与新历史无法对齐，产生重复提交与冲突。

---

## 卡片 8｜强推应使用 --force-with-lease

**核心知识：** rebase 后需要强推时用 `--force-with-lease`，远端被他人更新过则拒绝推送。

**简明解释：** `--force` 无条件覆盖远端；`--force-with-lease` 先比对远端状态，若他人已推送新提交则拒绝，避免覆盖别人的工作。

**例子：** `git push --force-with-lease`
